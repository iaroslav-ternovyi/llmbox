# llmbox: как им пользуются

Черновик продуктового дизайна от 2026-09-26. Решения, помеченные **?**, остаются за автором.

## 1. Для кого

Человек с одной машиной под локальные модели: игровой ПК или бокс с одной видеокартой на 8–24 ГБ и 32–128 ГБ RAM, иногда Mac. Модель ему нужна для конкретной работы: агент-программист, документы, тексты. Сейчас он тратит дни на три вещи:

1. **Выбор модели и кванта.** Каждую неделю выходят десятки моделей. Рейтинги вендоров завышены. Публичные бенчмарки меряют базовые модели, а не их GGUF-кванты.
2. **Подгонку под своё железо.** Приходится решать, какие эксперты держать в VRAM, какой брать контекст и какой тип KV-кэша, включать ли MTP, сколько потоков.
3. **Отлов скрытых поломок.** Бывают сломанный шаблон чата, петли в рассуждениях, вызовы инструментов, которые ломаются на квантованном KV-кэше.

Нашего бокса эти три проблемы стоили недели работы. llmbox должен сжать это до минут.

## 2. Сценарии

**A. «Что лучше всего запустить у меня?»** (сайт, без установки)
- Человек выбирает железо: пресет вроде «RTX 5070 12 ГБ + 64 ГБ DDR5» или свои числа (VRAM, RAM, пропускная способность памяти).
- Затем выбирает задачу: агентное программирование, документы, тексты или всё сразу.
- Получает рейтинг рецептов:
  - качество в процентах от фронтира с доверительным интервалом;
  - скорость на его железе: измеренная, если похожее железо уже присылали, иначе предсказанная из заголовка GGUF;
  - сколько задач в час модель решает на его железе;
  - одна команда установки.

**B. «Поставь и настрой»** (CLI)
```
llmbox host add            # один раз: определить железо, измерить пропускную способность RAM
llmbox install tiel-al     # скачать GGUF, подогнать рецепт под железо, записать лаунчер и llama-swap
llmbox tune tiel-al        # необязательно, 5–10 мин: подобрать скоростные ручки на реальных замерах
```

**C. «Проверь, что работает как обещано»** (CLI, по желанию)
```
llmbox bench tiel-al --tier quick   # ~30–45 мин: способности + скорость на своём железе
llmbox submit                       # отправить результат на сайт (подписанный, с рецептом и хешем модели)
```
Смысл проверки: найти поломки именно этой машины (кривой шаблон, драйвер, другая сборка llama.cpp) и добавить точку скорости для этого класса железа.

**D. «Вышла новая модель»** (автор кванта или энтузиаст)
```
llmbox scout <hf-repo>        # какие кванты влезут и с какой скоростью, без скачивания
llmbox recipe new <hf-repo>   # черновик рецепта: сэмплинг и шаблон с карточки модели, анти-петли по словарю
llmbox bench ... && llmbox submit
```

## 3. Рецепт или оптимизация: нужны оба, это два слоя

Главный вопрос: достаточно ли рецепта. Рецепта достаточно только на таком же железе. Поэтому рецепт делится на две части.

| слой | что в нём | от чего зависит | кто задаёт | влияет на качество? |
|---|---|---|---|---|
| **переносимый** | точный файл модели (репозиторий, файл, sha256), шаблон и его параметры (effort), сэмплинг, анти-петли (маркеры по словарю, детектор, запас на ответ), тип спекуляции (MTP), ограничения («только KV f16: у семейства Ornith ломаются вызовы инструментов») | от модели | автор рецепта, проверяется бенчмарком | **да**, к нему привязано число качества |
| **аппаратный** | размер контекста, раскладка GPU/RAM (fit, эксперты в RAM), batch/ubatch, потоки и привязка к ядрам, cache-ram, число слотов, глубина черновика MTP | от железа | **оптимизатор** на машине пользователя | нет, только скорость |

Как это работает:
- **fit** считается за секунды, без скачивания модели. Раскладка берётся из заголовка GGUF и профиля железа. Это уже умеют `estimate` и `scout`: предсказание по Tiel совпало с замером.
- **tune** занимает 5–10 минут. Это короткая сетка замеров по 2–3 ручкам, которые формула не предсказывает: ubatch, глубина черновика, потоки, «ещё один слой экспертов на GPU». Качество он не трогает, поэтому перемерять его не нужно.
- **Когда качество всё-таки надо перемерять:** если оптимизатору не хватает памяти и приходится брать меньший квант или квантовать KV-кэш. Это уже **другой рецепт** со своим числом. Молча такое делать нельзя. Правильно показать выбор: «Q4 не влезает при 128k; вот Q3 (качество −X по данным сайта) или Q4 при 64k».
- Выбор кванта — самый большой рычаг «качество ↔ скорость». Первая точка данных для сайта: кванты Tiel IQ3_XXS и Q3_K_XL против Q4, их прогоним после кампании.

Итог: пользователь берёт с сайта переносимый рецепт, а llmbox сам подгоняет аппаратную часть. Бенчмарк нужен только для проверки и для пополнения базы.

## 4. Из чего состоит продукт

1. **Клиент `llmbox`**, открытый код. Сейчас есть: host, scout, estimate, speed, recipe (render и check), bench, queue, validate, report.
   Нет: `install`, `fit` как отдельной команды, `tune`, `submit`, `recipe new`. Поддерживается только NVIDIA + Linux, Mac позже **?**
2. **Реестр рецептов**: git-репозиторий с переносимыми рецептами (TOML) и заметками, откуда каждое значение. Рецепт принимается PR с результатом бенчмарка.
3. **Схема результатов** (`results.py`): отпечаток железа, сборка llama.cpp, sha256 модели, полный рецепт, версия и хеш набора задач, числа рядом с предсказанием. Это уже есть.
4. **Приём результатов:** подписанный upload, фильтр выбросов, отдельная отметка «проверено нами» для прогонов на эталонном боксе. Скрытые задачи держим на сервере, чтобы тесты не утекли **?**
5. **Сайт**: статический, собирается из результатов и реестра, дешёвый хостинг.

## 5. Сайт: страницы

- **Главная.** Выбор железа и задачи, рейтинг рецептов. Первым показываем ответ на «что поставить», а не таблицу.
- **Рецепт или модель.**
  - Качество по блокам с доверительным интервалом и процентом от фронтира.
  - Скорость по глубине контекста (2k / 32k / 96k+): падение на длинном контексте важно для агентов.
  - Задач в час.
  - Рецепт с кнопкой копирования и объяснением каждой настройки.
  - Известные проблемы (петли, шаблон) и результаты пользователей на разном железе.
- **Сравнение** 2–3 рецептов бок о бок.
- **Железо**: что лучше всего на каждом классе видеокарт.
- **Методика**:
  - откуда 100% (фронтир-эталон на тех же задачах);
  - уровни набора задач;
  - защита от подгонки;
  - что значит доверительный интервал.
- **Скачать / как отправить результат.**

## 6. Дизайн

Текущий `leaderboard.html` сделан на системном шрифте, с зелёным акцентом и таблицей. Это «стандартный» вид, от него уходим. Нужна своя узнаваемая айдентика. План:
1. Собрать 3–4 разных визуальных направления на **реальных данных** кампании v0.9. Кандидаты:
   - лабораторный прибор (тёмный, цифры как на осциллографе);
   - редакционный (крупные числа, газетная типографика, рейтинг как история);
   - швейцарская спецификация (строгая сетка, один сигнальный цвет);
   - наследник культуры PC-бенчмарков (шкалы, перцентили, «твоя машина на N-м месте»).
2. Автор выбирает направление, из него собирается дизайн-система: шрифты, цвета, графики скорости и качества.
3. Сайт генерируется из этой системы.

## 7. Порядок работ

1. Кампания v0.9 и выбор 2–3 моделей для бокса. Идёт сейчас.
2. Разделить рецепт на переносимый и аппаратный слои. Добавить `llmbox fit`, частично это уже `estimate`.
3. Направления дизайна на данных v0.9, выбор, дизайн-система.
4. Сайт v1 только на наших результатах, чтобы проверить спрос.
5. `install`, `tune`, `recipe new`.
6. `submit` с подписью и сервер приёма. Сайт начинает принимать результаты пользователей.
7. Калибровка задач по IRT и адаптивный тест: 15–20 минут вместо 45.
