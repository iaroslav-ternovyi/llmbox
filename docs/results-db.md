# База результатов: хранение тестов всех пользователей

Проект, 2026-09-29. Сейчас результаты лежат JSON-файлами в `~/.llmbox/results/<host>/`, сайт собирается из них
на одной машине. Для сообщества нужна база, в которую пользователи присылают прогоны со своего железа, а сайт
строится из неё сам.

## 1. Главные решения

1. **Сырые данные неизменяемы, всё остальное производное.** Хранится то, что модель ответила (текст ответа,
   вызовы инструментов, время, токены), а не только баллы. Баллы, рейтинг и страницы в любой момент можно
   пересчитать заново. Это необходимо: грейдеры исправляются (например, парсер knowledge 2026-09-29), банк IRT
   перекалибровывается с каждым новым прогоном, версии набора задач меняются. Если хранить только баллы, всё
   это теряется.
2. **Качество не зависит от железа, скорость зависит.** Один и тот же файл модели (sha256) с одинаковыми
   переносимыми настройками (сэмплинг, шаблон, KV-кэш, speculative) даёт одинаковые ответы на любой машине.
   Поэтому ответы всех пользователей на этот файл объединяются в одну оценку: каждый новый прогон сужает её
   интервал для всех. Скорость, наоборот, хранится только вместе с машиной, на которой её замерили.
3. **Сервер не верит клиенту.** Балл клиента ни на что не влияет. Сервер сам пересобирает задачи из seed и
   перепроверяет присланные ответы тем же кодом, что и `llmbox` (§5).
4. **Сайт статический, данные из базы.** Страницы и JSON для них пересобирает воркер после каждого принятого
   прогона. Сайт отдаётся с CDN: он быстрый, дешёвый и не падает от нагрузки. Динамическое API нужно только для
   загрузки прогонов и для поиска.

## 2. Три слоя хранения

| Слой | Что лежит | Объём (оценка на 10 тыс. прогонов) | Где |
|---|---|---|---|
| Хранилище объектов | Пакет прогона целиком: JSON записи + трейсы рассуждений, gzip, по sha256 | ~2 ГБ сырых, ~0.4 ГБ в gzip | R2 / S3 |
| Реляционная БД | Метаданные, ответы по задачам (без больших текстов), замеры скорости, производные баллы | ~1 млн строк ответов, < 0.5 ГБ | Postgres (или SQLite/D1 на старте) |
| CDN | Готовые страницы и JSON-снимки для сайта | десятки МБ | Cloudflare Pages / R2 |

Большие тексты (ответы, трейсы) лежат в объектах, а в БД хранятся только ссылки на них. Так база остаётся
маленькой и быстрой, а перепроверку можно запустить, прочитав пакет прогона.

## 3. Модель данных

```
users ─┐
       └─< runs >── hardware_profiles ──> hardware_classes
            │  └──> model_files ──> models
            │  └──> settings (portable_hash, hardware_hash)
            │  └──> suites (version, content_hash)
            ├─< answers >── families (block.kind.Llevel, fingerprint per suite)
            └─< speed_points
banks (suite content_hash → IRT-параметры)      scores (модель+настройки × версия → балл, интервал, блоки)
```

**users**: id, github_id, имя, дата, репутация (число принятых прогонов), флаги (заблокирован).

**hardware_profiles**, то, что `llmbox host add` уже снимает сам:
- GPU (модель, VRAM, количество, драйвер, лимит мощности), бэкенд (CUDA / Metal / ROCm / Vulkan / CPU);
- CPU (модель, ядра, AVX-512), RAM (объём, тип и частота, **измеренная** скорость чтения ГБ/с);
- ОС, память Mac (unified).

Отпечаток профиля — хеш этих полей: одна и та же машина при повторных прогонах попадает в один профиль.

**hardware_classes**: грубая группа для сравнения, например «RTX 4090 24 ГБ + DDR5 ~80 ГБ/с + 64 ГБ» или
«Mac M4 Max 40-core 128 ГБ». Ключ: модель GPU × корзина скорости RAM × корзина объёма RAM × бэкенд. По классу
считаются медианы скорости и подбираются настройки «для такой же машины».

**models / model_files**: базовая модель (из цепочки HF `base_model`), репозиторий, файл, квант, sha256,
параметры (всего / активных), архитектура. sha256 сверяется с хешем файла на Hugging Face: только тогда модель
помечается «проверенный файл».

**settings**: две части рецепта, как в `llmbox/fit.py`:
- *переносимые* (сэмплинг, шаблон, KV-тип, speculative, анти-луп) → `portable_hash`. **Они задают балл.**
- *аппаратные* (контекст, раскладка, батчи, потоки, движок) → `hardware_hash`. Они влияют только на скорость.

**suites / families**: версия набора, content hash, семейства задач `block.kind.Llevel` с отпечатком из
`llmbox/famfp.py`. Отпечаток говорит, какие ответы из старых версий ещё годятся (так уже работает объединение
ответов).

**runs**: пользователь, профиль железа, файл модели, настройки, сборка движка (llama.cpp / ik / форк + коммит),
версия набора, режим (quick / adaptive), выданный сервером seed, время, статус (`received → verified → rejected`),
ссылка на пакет в хранилище, сводка телеметрии (температуры, мощность, VRAM).

**answers**, одна строка на задачу прогона:
- run_id, family, item_id, seed;
- балл клиента и **балл сервера**;
- секунды, токены, finish_reason, ошибка, флаги (обрезан, зациклился).

Это вход для IRT, текст ответа лежит в пакете.

**speed_points**: run_id / profile_id, файл, `hardware_hash`, глубина контекста, генерация tok/s, чтение
промпта tok/s, первое слово (с). Сюда же идут прогоны `llmbox optimize` (сток против рецепта).

**banks / scores**: производные таблицы. Банк IRT на content hash. Балл пары «файл + переносимые настройки»
на версию (оценка, интервал, блоки, число ответов и пользователей), место в рейтинге, группа.

## 4. Разное железо

- **Балл** пары «модель + переносимые настройки» считается по объединённым ответам всех пользователей и всех
  машин. Прогон на слабой машине так же полезен для оценки, как на сильной, просто он дольше идёт.
- **Скорость** показывается так:
  1. *замерено на твоём классе железа*: медиана и разброс, число машин и людей;
  2. если класс не мерили, *прогноз* по модели пропускной способности памяти (`llmbox/estimate.py`), с пометкой.
     Коэффициенты прогноза подстраиваются по всем замерам сообщества, для Mac отдельно (как `k2` сейчас).
- **Настройки «скопировать себе»** берутся от лучшего замера на ближайшем классе железа: тот же GPU и
  похожая RAM. Иначе из рецепта с `--fit`, который подгонит раскладку сам.
- **Выбросы.** Замер скорости в 2 раза выше медианы своего класса помечается и в медиану не входит, пока его не
  подтвердит второй человек.
- **Одинаковые машины разных людей** — главное доказательство скорости: на странице видно «замерено на 7 машинах
  RTX 4090, 4 человека».

## 5. Загрузка прогона и доверие

```
llmbox run --submit
   1. клиент: POST /runs/start (github-токен, модель, железо) → сервер выдаёт run_token и seed
   2. клиент гоняет адаптивный тест с этим seed, как сейчас
   3. клиент: PUT пакет (gzip JSON + трейсы) → хранилище, POST /runs/{id}/finish
   4. сервер (воркер Python): пересобирает задачи из seed, перепроверяет каждый ответ, пишет answers
      с баллом сервера, статус verified или rejected (с причиной)
   5. воркер: при N новых ответах перекалибровка банка → пересчёт scores → пересборка сайта
```

Как отбиваются подделки:
- **seed выдаёт сервер**, заранее выучить задачи или выбрать удачный seed нельзя;
- **баллы считает сервер**:
  - текстовые блоки перепроверяются по тексту ответа;
  - tools и agentic перепроверяются повтором присланного журнала вызовов в детерминированном мире задачи;
  - explain оценивает тот же читатель, что и сейчас (`llmbox/pending.py`), на машине проекта;
- **файл модели** проверяется по sha256 против Hugging Face;
- **скорость проверить нельзя**: она честно помечена «самоотчёт», подкреплена телеметрией и совпадением с
  другими машинами класса, выбросы исключаются;
- вход через GitHub, лимиты на число прогонов в день, бан по пользователю.

## 6. Как сайт получает данные

Воркер после каждого принятого прогона обновляет JSON-снимки и страницы, которые их используют:
- `ranking.json`: рейтинг текущей версии;
- `models/<id>.json`: модель, её настройки, прогоны, скорости по классам железа;
- `hardware/<class>.json`: что мерили на этом классе;
- `new.json`: лента новых моделей из `llmbox watch`.

Страницы остаются статическими, как сейчас, но число на сайте всегда соответствует базе. Полный рендер занимает
секунды. Поиск и фильтры «моё железо» работают в браузере по JSON-снимкам. Для редких запросов (история
прогонов пользователя) есть API.

## 7. Где держать

| Вариант | Состав | Цена на старте | За | Против |
|---|---|---|---|---|
| **A. Cloudflare** | Pages (сайт) + Workers (API) + D1 (SQLite) + R2 (пакеты) | $0–5/мес | нет платы за трафик, один провайдер, D1 — та же SQLite, что локально | D1 до 500 МБ на базу на бесплатном; Python-воркер для перепроверки нужен отдельно |
| **B. Supabase** | Postgres + GitHub-вход + Storage + Edge Functions | $0 (пауза после недели простоя), дальше платный Pro | вход и хранилище готовые | 500 МБ базы на бесплатном; Python-воркер отдельно |
| **C. Один VPS** | Postgres + FastAPI + Caddy + воркер на одном сервере (~€5/мес), сайт на Cloudflare Pages | ~€5/мес | всё в одном месте, воркер на Python рядом с базой, нет лимитов провайдера | админить самому, бэкапы самому |

Рекомендация: **сейчас SQLite локально** (та же схема), затем **A**, когда появятся первые чужие прогоны. Пакеты
лежат в R2, метаданные в D1, перепроверка и IRT идут в Python-воркере на VPS или на коробке.

SQLite → D1 переносится без переписывания схемы. Если база вырастет за 500 МБ или понадобится аналитика,
переход на Postgres (C) — это смена драйвера, схема та же.

## 8. План

1. **Локальная база — сделано 2026-09-29** (`llmbox/db.py`, `llmbox db sync|stats|sql`). 341 результат, 2906
   ответов, 257 точек скорости; база 1.2 МБ, импорт 0.5 с. Пакеты — `~/.llmbox/bundles/<sha256>.json.gz`, у
   переписанного файла сохраняется история версий. Читатели (`results.files`, report, irt, site) берут данные из
   базы (`LLMBOX_NO_DB=1` — прямо из файлов). Сайт из базы и из файлов совпал на всех 137 страницах, калибровка
   IRT тоже (135 семейств, 20 моделей, 1369 ответов). Писатели пока пишут JSON-файлы, база их подхватывает.
   Исходный план шага: `~/.llmbox/llmbox.db` (SQLite) со схемой §3. `llmbox import` переносит все
   JSON-результаты. Новые прогоны пишутся в базу и в JSON, пакеты как сейчас. `report.rows()` и сайт читают из
   базы. Проверка: сайт из базы совпадает с сайтом из файлов.
2. **Серверная перепроверка (2–3 дня).** Модуль `llmbox verify <пакет>`: пересобрать задачи из seed,
   перепроверить ответы, выдать answers с баллом сервера. Сначала на наших же прогонах: балл сервера = балл
   клиента.
3. **API и загрузка (3–5 дней).** Worker: `/runs/start`, `/runs/{id}/finish`, вход через GitHub,
   `llmbox run --submit`. Пакеты в R2, метаданные в D1.
4. **Воркер пересчёта.** Очередь принятых прогонов → verify → перекалибровка по порогу → scores → пересборка
   сайта → публикация на Pages.
5. **Страницы железа.** Классы железа, скорость по классам, «замерено на N машинах», настройки ближайшего класса.

## 9. Открытые вопросы

- Публиковать ли тексты ответов (прозрачность против размера и приватности)? Предложение: для cloud-моделей и
  наших прогонов да, для пользовательских по согласию.
- Читатель explain работает на нашей машине: при большом потоке прогонов нужна очередь или облачный читатель
  (но тогда тот же для всех, иначе баллы несравнимы).
- Нужна ли модерация новых моделей (кто-то зальёт файл с чужим названием): связывать по sha256 и цепочке
  `base_model` на HF, не по названию.
