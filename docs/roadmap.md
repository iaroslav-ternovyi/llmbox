# llmbox: что осталось до запуска

План от 2026-09-30. Решения, помеченные **?**, остаются за автором.

## 1. Задача сервиса

Человек с одной машиной (ПК с видеокартой, бокс, Mac) хочет три вещи:

1. **Подобрать** лучшую локальную модель под своё железо и свою работу.
2. **Оптимизировать** её запуск: выжать из железа всю скорость, не трогая качество.
3. **Сравнить** с другими: кто на самом деле умнее и кто быстрее. Сравнение идёт по замерам людей с таким же
   железом, а не по заявлениям авторов.

## 3. Кто рядом (исследование 2026-09-30)

- **LocalMaxxing** (с апреля 2026) — ближайший конкурент: 2,6 тыс. пользователей, 8,5 тыс. прогонов.
  - Вход через GitHub, API-ключ, не больше 1 прогона в минуту.
  - Классы железа (GPU / unified / CPU): лучший, медианный и худший результат.
  - Качество по GSM8K, HellaSwag, HumanEval+ и Terminal-Bench 2.1, каждый прогон вручную одобряет админ.
  - Нет: подбора настроек, качества конкретного кванта относительно фронтира, свежих задач (публичные наборы
    могут протечь в обучение), скорости на длинном контексте.
- **LocalScore** (Mozilla) почти заброшен: около 4,2 тыс. результатов.
  - Нет ни входа, ни защиты: балл клиента сохраняется как есть.
  - Железо не нормализовано: у одной модели 826 отдельных «ускорителей».
  - Устаревшая сборка llama.cpp занижает AMD, Windows и Mac в 2 раза, и эти результаты так и висят.
- **Таблицы llama.cpp на GitHub** (Apple, CUDA, Vulkan, ROCm): им доверяют, но они про Llama-2-7B Q4_0 и
  собираются вручную.
- **llm-bench.io** оценивает качество LLM-судьёй. **Token Atlas** (с 2026-09-26) собирает скорость из
  источников, без качества.

**Наше отличие:**
- качество точного файла модели на свежих задачах, проверенных программами, в % от Opus с интервалом;
- скорость на глубине контекста, как у агента;
- настройки, подобранные под машину;
- установка одной командой ровно того, что измерено.

## 4. Как устроено сравнение между пользователями

Берём из опыта Geekbench, 3DMark, UserBenchmark, OpenBenchmarking и LocalScore:

1. **Железо нормализуется с первого дня.**
   - Видеокарта: (производитель, чип, VRAM). Apple: (чип, ядра GPU, память). Исходная строка хранится отдельно.
   - Класс = видеокарта × корзина скорости RAM × бэкенд. Скорость RAM нужна потому, что у MoE эксперты живут в RAM.
   - Отдельные проценты (перцентили) показываем, когда в классе 5 машин и больше. До этого показываем «N машин»
     и сами числа.
2. **Распределение, а не рекорд.** По классу показываем медиану, 5-й и 95-й перцентили и «твоя машина:
   58-й перцентиль из 14 таких же». Рейтинг строится по медиане. Замер выше медианы класса в 2 раза или выше
   прогноза в 2 раза помечается как выброс и не входит в медиану, пока его не повторит второй человек.
3. **Ключ конфигурации.** Для каждого замера хранятся движок и его коммит, флаги (аппаратный хеш), sha256
   файла и версия теста. Замеры с разными движками не смешиваются, старые сборки помечаются.
4. **Доверие.**
   - Скорость проверить нельзя: она идёт как самоотчёт, анонимно, по id установки, с лимитами.
   - Качество принимается только после входа через GitHub device flow. Секрет клиента для этого не нужен,
     сервер проверяет токен и выдаёт свой ключ.
   - Задачи генерирует сервер (seed), баллы считает он же (`verify`).
   - Один набор ответов на задачу от одного человека. Банк задач не публикуется.
   - Ручного одобрения, как у LocalMaxxing, нет.
5. **Открытые данные.** Регулярный дамп базы. Пользователи LocalScore просили именно этого.

## 6. Скорость и удобство сайта

- Сейчас всё быстро: главная 103 КБ (на CDN со сжатием около 20 КБ), 34 мс, 2560 элементов.
- С ростом данных узкое место — встроенные DATA. Замеры по классам будут лежать в `data/<модель>.json` и
  грузиться при открытии модели. Главная получает только медианы классов.
- Сборка из базы остаётся статической. После приёма пересобираются только затронутые страницы.
